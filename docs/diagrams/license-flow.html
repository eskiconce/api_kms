Flujo de Licencias Widevine

Secuencia completa desde el Player hasta la licencia firmada

📱 Player
⚡ KMS API
⚡ Redis
🗄️ MySQL
🔐 DRM Provider
1
Player solicita licencia
El Player envía el challenge Widevine (contenido binario) con el header X-DRM-KID que identifica la key ID del contenido.
POST /wv/license
X-DRM-KID: a1b2c3d4e5f67890...
Content-Type: application/octet-stream
[challenge binary data]
2
KMS valida el KID
La API verifica que el header X-DRM-KID esté presente. Si falta, retorna HTTP 400.
3
Lookup de key en Redis (caché)
Primero intenta obtener la key desde Redis con key pattern drm:key:{kid}. TTL de 6 horas.
REDIS GET drm:key:a1b2c3d4...
→ "00112233445566778899aabbccddeeff"
4
Fallback: MySQL (si Redis miss)
Si Redis no tiene la key o no está disponible, consulta MySQL directamente la tabla content_keys.
SELECT content_key FROM content_keys
WHERE kid = 'a1b2c3d4...'
5
KMS envía challenge al DRM Provider
Con la key validada, reenvía el challenge binario al proveedor DRM Widevine para firma.
POST {DRM_PROVIDER_URL}
Content-Type: application/octet-stream
[challenge binary data]
6
DRM Provider firma la licencia
El proveedor firma el challenge con su private key y retorna la licencia Widevine en formato binario.
200 OK
[signed license binary]
7
KMS retorna licencia al Player
La licencia firmada se retorna al Player como application/octet-stream. El Player puede ahora descifrar el contenido.
200 OK /wv/license
Content-Type: application/octet-stream
[signed license binary]
💡 Nota sobre Key Rotation
Cuando se rota una key (POST /api/keys/rotate), la key anterior permanece válida en MySQL para contenido VOD ya empaquetado. Solo la key "activa" del canal cambia para nuevo contenido live.
